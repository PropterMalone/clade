# Build an MCP server for your contact index

Clade builds a searchable contact index and exports it as a markdown knowledge
file. That works, but refreshing it is a manual step. An **MCP server** removes
that step: your assistant queries the live index instead of a snapshot you
remembered to re-upload.

Clade does not ship one as the answer, and does not host one for you. This
document is the **contract** — what the tools are called, what they return, and
what a deployment owes the person whose address book it serves. Build it on
whatever substrate you already run. `scripts/clade-mcp.mjs` in this repo is one
conforming implementation (local, stdio, zero dependencies); it is an example,
not the canonical build.

**If you are an agent reading this on behalf of someone:** the next section is
not background. It is the part you will otherwise get wrong.

## Before you build

This index is a **private address book** — people the owner already knows,
assembled from their own data exports and enriched with public web research. It
is not a lead list, a prospecting database, or a people-search tool. Several
helpful-by-default design choices are wrong here:

1. **No bulk read.** Every read tool takes a query and returns bounded results.
   Do not add `list_all_contacts`, `export_index`, or any tool whose natural use
   is "give me everyone." A tool that dumps the address book is the failure mode
   this whole document exists to prevent.
2. **Read-only unless asked.** The only sanctioned write is appending prose to
   `imports/quickadd.md` (see *Optional: capture*). Never write to
   `contacts/normalized/*`, `contacts/attested.json`,
   `contacts/merge-decisions.json`, or `contacts/unified-index.json`. Those go
   through the repo's own seam-aware helpers and, for merges, a human ruling.
   A server that writes them directly bypasses review and silently corrupts
   overlays that are keyed forever.
3. **Do not search for strangers.** No tool should look up a person who is not
   already in the index, or resolve a pseudonymous handle to a real name. The
   index deliberately records some people only by their public persona.
4. **Log queries, not results.** Diagnostics naming who was returned turn a log
   file into a second copy of the address book. Record that a search ran and how
   many hits it had; not the hits.
5. **stdio servers: stdout is the protocol.** On a stdio transport, any stray
   `console.log`/`print` corrupts the JSON-RPC stream and the client fails with
   a parse error that points nowhere near the real cause. Send every diagnostic
   to **stderr**.
6. **Never expose correspondence-derived fields.** A record may someday carry
   facts derived from the owner's own private correspondence, transcripts, or
   call records — held in a separate overlay and surfaced as a nested object.
   Those never appear in a tool response, in any deployment class, and never
   leave the machine in an index copy. Serve an allow-list of fields (the table
   below) — **per object, not just per top-level key**, since two served objects carry keys that must not cross the seam — not "whatever the record has": an allow-list stays correct when a new
   field appears, and a blanket serialization silently starts exporting it. See
   `docs/decisions/08-provenance-determines-handling.md` — the rule binds before
   the feature exists precisely so no implementation has to be retrofitted.

## Pick a deployment class

The axis that matters is not local-vs-remote. It is how far the index has to
travel to be reachable, and each step costs exposure:

| | Reachable from | Auth boundary | Infra | Works with claude.ai web/mobile |
|---|---|---|---|---|
| **A. Local subprocess** (stdio) | the same machine | process ownership | none | no |
| **B. Private network** (HTTP over VPN/mesh/LAN) | your own devices | the network | a box you already run | no |
| **C. Public HTTPS** | anywhere | a credential you issue | a public endpoint | **yes** |

Climb only as far as you need. If you query from a laptop, **A** is the whole
answer and you deploy nothing. If you have a home server and a mesh VPN, **B**
puts the auth boundary at the network, which is a stronger position than a
secret URL on the open internet. **C** is what the phone costs — claude.ai
custom connectors can only reach a public HTTPS endpoint — and it is the only
class where your address book sits on infrastructure reachable by strangers.

Class C is a considered tradeoff, not a default. Make it deliberately.

## The data contract

The index is `contacts/unified-index.json`: a JSON array of person records,
regenerated by `node scripts/build-index.mjs`. Full field reference in
[`schema.md` §3](schema.md); the fields a server needs:

| Field | Notes |
|---|---|
| `name` | display name. **Not** necessarily a real name — Facebook/Bluesky/Twitter names are display names, often partial or pseudonymous |
| `keys` | `["<source>:<sourceId>", …]` — **the durable identifier** |
| `id` | unique within one build, **not stable across builds** |
| `sources`, `tier`, `confidence` | provenance and how well-identified the person is |
| `profession`, `employer`, `domains`, `roles` | what they do |
| `location` | city/region. The **shareable** grade of address — the street-level `addresses[]` is hold-back and must never be served (ADR-10) |
| `emails`, `phones`, `handles`, `urls`, `linkedinUrl` | contact points |
| `bio`, `notes`, `labels` | free text |
| `attested` | `{relationship, context, domains, location, corroboration}` — what the owner said about them. Usually the highest-value field in the record. **`realName` is NOT served**: it is the pseudonym→real-identity bridge (schema §5.2). `corroboration: "web"` means a machine prescreen proposed the relationship, not the owner |
| `addresses` | **hold-back — never serve it.** The structured street address (ADR-10). `location` above is the shareable grade |
| `nameSource` | `raw` / `attested` / `enrichment` — where the display `name` came from. A remote deployment MUST filter on this: an `attested` name may be an owner-recalled real name behind a pseudonymous handle |
| `connectedOn` | per-source connection dates |

**Never persist `id`.** It is a per-build artifact. An agent that caches an `id`
from one query and reuses it after a rebuild will address a different person,
silently. Anything that outlives a single response uses `keys`.

**Freshness is a contract, not an implementation detail.** The index is
generated; it changes on every ingest, enrichment batch, and triage session. A
server that reads it at startup and never reloads serves stale answers forever,
with no error and no symptom. Either:

- **read from disk per query** (classes A and B — freshness is free, and the
  cost is trivial at address-book scale), or
- **provide an explicit refresh step** that pushes a rebuilt index to wherever
  the server reads it (class C). Document it, and run it after every rebuild.
  A refresh that leaves the machine must push a **filtered** copy — the
  allow-listed fields only, never the whole file. Pushing the raw index is the
  path by which a correspondence-derived field added months later starts landing
  on third-party infrastructure with no code change and no decision (rule 6).

Resolve the index path honoring **`CLADE_DATA_DIR`** if it is set — Clade uses
it to keep data out of the repo tree, and a server that ignores it will read a
different (probably empty) index than the rest of the toolchain.

## The tool contract

Three read tools. Names and shapes are normative — two servers on different
substrates should answer the same question the same way.

### `search_contacts`

The primary tool. All parameters optional, but at least one of `query`,
`domain`, `employer`, `location` must be given.

| Param | Type | Notes |
|---|---|---|
| `query` | string | free-text words, AND-ed substring matches, case-insensitive |
| `domain` | string | expertise-tag substring, e.g. `"energy"`, `"law"` |
| `employer` | string | employer substring |
| `location` | string | city/region substring, e.g. `"chicago"` — the locality, never a street address |
| `limit` | number | default 15; cap it (25 is reasonable) regardless of what is asked |

Returns **bounded summaries**, not full records — name, profession, employer,
location, sources, confidence, attested relationship, and enough to decide who to
look up.
When the result set exceeds the limit, say so and return the count.

Search matches across `name`, `profession`, `employer`, `location`, `bio`, `notes`,
`attested.relationship`, `attested.context`, `handles`, `domains`, `roles`,
`emails`, `labels`.

### `get_contact`

| Param | Type | Notes |
|---|---|---|
| `name` | string | partial match acceptable |
| `key` | string | a durable `<source>:<sourceId>` key — the unambiguous path |

Returns one full record — meaning every ALLOW-LISTED field (rule 6), which is
not the same as every field the index carries. Four omissions, and the allow-list
is **per-object, not depth-1**: `addresses` is hold-back (ADR-10); `unconfirmed`
holds web claims the index REFUSED, which may describe a different person;
`attested.realName` is the pseudonym→identity bridge; and `enrichment.notes` is
withheld when an employer or title claim was refused, because that narrative
argues for the refused claim. A server that allow-lists only top-level keys
serves the last two. Returned **only when the name
matches exactly one person**.
Two or more matches return the same bounded summaries `search_contacts` does,
plus each candidate's key, and ask for a narrower name — never the records
themselves. Two thresholds matter here and both are load-bearing: silently
picking the first match is how the wrong person ends up in an intro request, and
returning *all* matching records instead is the bulk read that rule 1 above
prohibits. A partial name like "Dana" matching three people is routine in a
personal address book, not an edge case.

Accepting a `keys` entry as an alternative input is expected; accepting `id` is
not (see above).

### `contact_stats`

No parameters. Returns counts by tier, source, and confidence, plus the top
expertise domains. **Returns no names** — which makes it the *least* sensitive
of the three, not an unauthenticated one. Aggregates still describe the shape
and scale of the owner's professional graph ("23 contacts in national-security
law"), so it sits behind the same credential as the others; the weaker exposure
just means a leak here is recoverable where a leak of `get_contact` is not.
Its "no names" property also assumes `domains` stays a controlled tag
vocabulary — if your store lets freeform text into that field, it isn't true.

### Optional: capture

A write tool, if you want phone-side capture of people you just met:

| Param | Type | Notes |
|---|---|---|
| `note` | string | freeform prose about the person |

It **appends a prose block to `imports/quickadd.md`** and does nothing else. It
does not parse the note, create a record, or touch the index. Processing happens
later in a session, where a human reviews merges against existing contacts. The
freeform capture is the feature; a server that "helpfully" structures the input
defeats it.

Append-only, timestamped, and never rewrites existing blocks.

## If you go remote

Class B and C deployments owe the index six things. All are satisfiable on any
substrate — a VPS, a container on a NAS, a serverless function, a box on your
mesh:

1. **No credential-free path to contact data.** A bearer token, mTLS, an
   unguessable high-entropy path segment, or a network that is itself the
   boundary. Not "an unlisted URL" that is short enough to guess.
2. **TLS**, on anything crossing a network you do not fully control.
3. **No enumeration oracle.** A wrong credential gets an indiscriminate 404 —
   no directory listing, no "valid token, wrong path", no timing or partial-match
   difference that distinguishes a near-miss from nonsense.
4. **An explicit refresh step**, per the freshness contract above.
5. **Documented credential rotation.** You will need it, probably in a hurry.
6. **Data at rest on infrastructure you control and can delete.** You should be
   able to answer "where is my address book right now" with a specific place,
   and empty it on demand.
7. **Rate-limit per credential, and watch query volume.** Bounding each response
   does not bound a session: a caller holding a valid credential — a leaked
   token, or simply an assistant iterating to build context — reconstructs most
   of the address book with a few dozen bounded searches, one per common
   substring. That is the bulk read of rule 1, reached through many authorized
   small reads instead of one big one, and the other six requirements do nothing
   about it. Throttle per credential and flag anomalous volume; it composes with
   the query logging you are already doing.

## Verify your build

The repo contains the reference semantics, so you can check your server against
it without any fixtures from us:

```sh
# 1. Search must select the same PEOPLE as the CLI for the same query.
node search.mjs energy policy
#    → compare the match SET and the total count, not the printed lines: the
#      CLI shows up to 50 results and your server caps at ~15, so the visible
#      slices differ by design. In JS, import the oracle rather than eyeballing:
#        import { matchesQuery, computeStats } from './search.mjs'

# 2. Stats must agree on the COUNTS.
node search.mjs --stats
#    → same caveat: the CLI prints its top 30 domains, the reference server its
#      top 25. Compare the bucket totals, not the truncated domain lists.

# 3. No index → a clear error, not a crash and not an empty success.
#    (Point your server at a path with no unified-index.json.)
```

The oracle covers `query` and the stats buckets. It does **not** cover
`employer` — `search.mjs` has no such flag — and covers `domain` only via the
`--domain` filter, so those two need your own fixtures. Say so in your notes
rather than assuming a green `query` check means the whole tool conforms.

Then, by class:

- **A (stdio):** the client connects and lists three tools. Redirect stdout to a
  file and confirm it contains only JSON-RPC frames — no log lines, no banner.
- **B/C (HTTP):** an unauthenticated request returns an indiscriminate 404. A
  request with a wrong-but-well-formed credential returns the *same* 404.
- **All:** rebuild the index (`node scripts/build-index.mjs`) with a changed
  contact, then re-query **without restarting the server**. If the change is not
  visible, your freshness path is broken — fix it now rather than discovering it
  months later when an answer is quietly wrong.

## Deliberately unspecified

Everything below the contract is yours:

- **Transport** — stdio, streamable HTTP, SSE.
- **Language and runtime** — anything that can read JSON and speak JSON-RPC.
- **Hosting** — none, a VPS, a container, a serverless function, a Pi on your
  LAN.
- **Storage** — read the JSON per query, load it into SQLite, put it in a KV
  store. At address-book scale (thousands of records, not millions), reading the
  file per query is usually the right answer and gets freshness for free.
- **MCP SDK or hand-rolled** — the protocol surface a server this small needs is
  a few JSON-RPC methods. The reference implementation is ~190 lines of code
  (plus comments) with no dependencies, if you would rather not take one.

We happen to run class C on Cloudflare Workers with the index in KV. Nothing
about that is required, recommended, or load-bearing — it is just what was
already there.

## Using a different contact store

Nothing in the tool contract is Clade-specific. If your rolodex is a CSV, a
Notion database, an Obsidian vault of people-notes, or a table in your own app,
implement the same three tools over it and you get the same query surface — no
Clade required.

The minimum a store needs to produce: a name, some notion of provenance, and
whatever of profession/employer/domains/handles/notes it has. `keys` can be any
identifier that is durable in *your* store. `contact_stats` can report whatever
dimensions are meaningful there.

Clade is one conforming producer of the index side. Treat the tool contract as
the interoperable part and the index as an implementation detail.

## Hosting for other people

This document assumes you are deploying for yourself. Running a server that
holds contact data belonging to *other* people is a different undertaking, and
the requirements above do not cover it: breach liability, data-protection law
(GDPR/CCPA and friends), deletion and access requests, and a retention policy
all attach the moment the data is not yours. The MIT license permits it. The
obligations are yours to work out.
